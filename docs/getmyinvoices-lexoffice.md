# GetMyInvoices → Lexware Office (lexoffice) — can Zold flow into it?

Asked for by WeLoveAccounting (call, 10 Sep 2026). They book exclusively in
Lexware Office (the product formerly called lexoffice) and use
GetMyInvoices ("GMI") as the collection layer that pushes into it. The
question was whether a Zold account can be made to flow through that pipe
without manual work.

Short answer: **the document half is fully automatable today, the bank-movement
half is not.** The break is on lexoffice's side, not GMI's, and it is a hard
one — Lexware Office's public API has no bank endpoint at all.

Everything marked VERIFIED below was read from the live API specification or
the vendor's own developer documentation today. Nothing has been called with a
real credential: we hold neither a GMI API key nor a Lexware Office one.

## What Lexware Office's public API can do — VERIFIED

Read from `developers.lexware.io/docs` on 10 Sep 2026. The API exposes
articles, contacts, countries, credit notes, delivery notes, dunnings, down
payment invoices, event subscriptions (webhooks), files, invoices, order
confirmations, payments, payment conditions, posting categories, print
layouts, profile, quotations, recurring templates, vouchers and voucherlist.

Bearer key, generated by the account owner at
`app.lexware.de/addons/public-api`. Rate limit **2 requests per second**.

**There is no bank account resource and no way to create or import a bank
transaction.** That is the finding that shapes everything else. A voucher can
be created and a PDF attached to it, so receipts and invoices go in cleanly;
the money movement that pays them cannot.

Their own answer to an unconnectable bank is an *offline account* whose
transactions are imported from a CSV or MT-940 file, through the UI, under
Finance → Accounts → Import transactions. The column mapping is set up once
per format and reused. (From their help centre, not tested.)

This matters to us specifically because a Zold euro account is a Monerium
e-money account with an IBAN at LHV Pank. Lexware Office's automatic bank
connection is a PSD2 login to the account holder's own bank, and the customer
has no LHV online banking to log into — the account is Monerium's. So the
"just connect the bank" path is closed regardless of the API.

## What GetMyInvoices' API can do — VERIFIED

Read from the live OpenAPI 3.0 spec at
`https://api.getmyinvoices.com/accounts/v3/doc/api.json`, server
`https://api.getmyinvoices.com/accounts/v3`. Note that **v2 is dead** — it
answers 410 and was shut down on 2024-10-01. Any integration guide pointing at
v2 is stale. Auth is an API key from the account dashboard
(`app.getmyinvoices.com/api_access`).

Two endpoints carry this integration.

**`POST /documents`** — upload a document. Required: `fileName`,
`fileContent` (base64), `documentType` (e.g. `INCOMING_INVOICE`). Optional and
all of it useful to us: `companyId`, `documentNumber`, `documentDate`,
`documentDueDate`, `paymentMethod`, `paymentStatus`, `paidAt`, `netAmount`,
`grossAmount`, `currency`, `vat` (an array, so several rates on one document),
`taxRates`, `lineItems`, `tags`, `note`, and `runOCR`.

That field list maps onto what Zold's invoicing module already computes. We
hold integer cents, VAT rounded once per rate bucket, and the issued snapshot
of both parties — so we can send the numbers rather than let OCR guess them.
Send `runOCR: false` where we know the figures; letting OCR re-derive a total
we already hold exactly is how a cent-level disagreement gets into someone's
books.

There is also `POST /documents/exists` (hash check) — the idempotency handle,
so a re-run does not double-file a document.

**`POST /bankAccounts/{bankAccountUid}/transactions`** — add a transaction.
Required: `bookingDate`, `valueDate`, `description`, `amount`. Optional:
`currencyCode`, `clientIban`, `clientBankCode`, `clientAccount`, `creditorId`,
`paymentPartnerName`, `transactionType`, `tags`.

That is, field for field, what the `sevdesk-monerium` mirror already builds
from a Monerium order (counterparty name, counterparty IBAN, memo as the
purpose, credit for an `issue`, debit for a `redeem`).

And `POST /bankAccounts/{uid}/transactions/{uid}/assign` assigns a document to
a transaction — the matching step, drivable from our side, since we know which
transfer paid which invoice and their bookkeeper would otherwise re-derive it
by hand.

**The one manual setup step:** there is no `POST /bankAccounts`. The spec has
GET, PUT, DELETE and archive, and bank accounts carry an `accountType` whose
example value is `CUSTOM`. So the customer creates the custom (CSV-upload)
bank account once in the GMI UI, and from then on we push transactions into it
by API. One click at setup, never again.

## Where it breaks, and the honest shape of the fix

GMI's Lexware Office sync account is a **document** export. Their own
integration page and the setup instructions describe receipts and invoices
moving across; nothing in either says bank transactions do. Bank movements
leave GMI as an **MT-940 export**, which they document for DATEV and "other
common accounting systems", and which Lexware Office can import into an
offline account.

So the realistic pipeline is two lanes of different quality:

| lane | path | manual work |
|---|---|---|
| invoices, receipts | Zold → `POST /documents` → GMI sync → Lexware Office | none after setup |
| bank movements | Zold → `POST .../transactions` → GMI → MT-940 export → Lexware Office import | one file, per period |

Calling that "flows without any problems" would be overselling it by exactly
one file drag per bookkeeping run. Worth saying to them in those words — a
bookkeeper who is told it is fully automatic and then finds a monthly file
step will trust the rest of it less.

Three ways to close the gap, in the order I would try them:

1. **Ask GMI directly** whether their Lexware Office export carries
   transactions as well as documents, or is on their roadmap. Their help
   pages are written for end users and are not a specification; a support
   answer settles it in a day and might make the second lane disappear.
2. **Ask WeLoveAccounting what they do today** for their other clients whose
   banks are not connectable. If they already run an MT-940 import each month,
   our second lane costs them nothing new and this is a non-issue. This is the
   cheapest question and should be asked first.
3. **Skip GMI for the bank half** and hand the bookkeeper a Lexware-Office-
   shaped CSV directly from Zold. Their CSV import is a documented,
   column-mapped format, set up once. It removes a hop rather than adding one,
   but it splits the pipeline across two tools, which is what they were trying
   to avoid by standardising on GMI.

## What we already have that feeds this

`~/Documents/sevdesk-monerium` is the same integration built for sevDesk, and
its seam is in the right place: `monerium.ts`, `chain.ts`, `mapping.ts` and
`state.ts` are provider-agnostic, and only `sevdesk.ts` knows the target. A
GetMyInvoices target is a new file beside it, not a new project. The rules
that repo already enforces carry over unchanged and are the ones that matter
here:

- only **processed** orders are mirrored — `placed`, `pending` and `rejected`
  are not bank movements, and a line in the books for a payment that may still
  be rejected is the one record this must never make;
- the mint and burn legs of an order are folded onto that order by tx hash, so
  nothing is booked twice;
- an on-chain movement matching no visible order is **reported, not booked**;
- it remembers which order became which row, so re-running is cheap and
  idempotent.

On the document side, Zold already issues A4-printable invoices with the
jurisdiction rules applied, and account documents (statements, transfer
receipts, balance and ownership proofs) under a verification code. Those are
the PDFs that would go up through `POST /documents`.

## Open questions before building

- Does the GMI → Lexware Office sync carry transactions? (Ask GMI.)
- What does WeLoveAccounting do today for unconnectable banks? (Ask them.)
- Which GMI plan tier includes API access, and does the accountant's own GMI
  licence cover a client account, or does each client need their own?
- Whose credential is it? A key per client account means the customer pastes a
  GMI API key into Zold, which is the shape the Monerium connector already
  uses and should reuse rather than reinvent.
- Does their GMI account want our **outgoing** invoices as well as the bank
  movements, or do those already reach Lexware Office another way?
